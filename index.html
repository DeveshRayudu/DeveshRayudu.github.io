Takes two satellite images from different sensors and makes them directly comparable: same units, same grid, aligned to a fraction of a pixel. Built at ISRO NRSC as the Radiometric Alignment project.

  • Python
  • GDAL / rasterio
  • OpenCV
  • PyQt5
  • 14+ modules
  • CLI + desktop GUI
  • 17 of 17 tests passed
  1. 1

    Input validation

    Checks the coordinate system, nodata values, and how much the two images overlap before any work starts.

    Under the hood

    Along the way this caught real problems: coordinate-system mismatches on LISS-class GeoTIFFs, a nodata override applied unconditionally, and a wrong denominator in the overlap percentage.

  2. 2

    Radiometric correction

    Converts raw pixel values (DN) to top-of-atmosphere reflectance, using each sensor's own solar irradiance and spectral response.

    Under the hood

    Supports Cartosat, LISS-3/4, Sentinel-2 (L1C) and Landsat, with the real Landsat-8 OLI response data. It runs at the start of the pipeline, before resampling, which removed a double-correction bug. Earth-sun distance comes from a lookup table.

  3. 3

    Footprint intersection and cropping

    Works out the true polygon overlap of the two images and crops both to the shared area.

    Under the hood

    Uses shapely and rasterio for the footprint geometry, so the crop follows the real overlap instead of a bounding box.

  4. 4

    Resampling to a common grid

    Brings both images onto the same pixel grid, using blur-aware block averaging or GDAL's bilinear, cubic, nearest or average methods.

    Under the hood

    The blur-aware path applies a Gaussian PSF pre-blur and then area-weighted block averaging, a from-scratch resampler checked against GDAL. A separate bilinear copy is used for registration, so the blur does not hurt matching.

  5. 5

    Sub-pixel registration

    Refines the geometric match between the two images with ECC alignment (Euclidean or affine motion).

    Under the hood

    I started with ORB + RANSAC and switched to ECC for sub-pixel accuracy. Farneback optical flow then double-checks the remaining shift.

  6. 6

    Homogeneity detection

    Finds the spatially uniform areas, where comparing two sensors is most trustworthy.

    Under the hood

    Combines coefficient of variation, local standard deviation and GLCM-based texture checks.

  7. 7

    Cross-sensor regression and diagnostics

    Fits the relationship between the two sensors' values and produces plots to judge the result.

    Under the hood

    Reduced Major Axis regression, with Theil-Sen as an outlier check. Plots include error histograms, shift-arrow grids and hexbin scatter plots.

  8. 8

    Logging and outputs

    Saves the aligned rasters, the diagnostic plots, and two run logs: a short summary and a full technical log.

    Under the hood

    Every run writes to its own timestamped folder, so results can be compared and reproduced.

What comes out. Aligned and cropped rasters, a common-region composite, diagnostic plots and run logs. In the final report, the sub-pixel residual stayed under 0.5 px, and a Landsat-8 vs Sentinel-2 example had 91% overlap with an ECC shift of about 0.04 by 0.07 px. Limits: reflectance only (no atmospheric correction) and clear-sky scenes.

A Python re-implementation of the DOE-DTL research paper: spot a DLDoS attack on a software-defined network, locate the attacking IP addresses, and block them.

  • Python
  • P4 / BMv2
  • Mininet
  • ELM classifier
  • Whale Optimization
  • P4Runtime
  1. 1

    Count the traffic

    A data-statistics module in the network switches keeps running counters of the packets passing through.

    Under the hood

    On real switches this is a P4 program on BMv2. For offline testing, a Python simulation mimics the same registers.

  2. 2

    Pre-detect

    A coarse check in the control plane flags traffic that looks unusual.

    Under the hood

    This is the paper's traffic-monitoring module.

  3. 3

    Extract features

    Turns the packet stream into features over multiple sliding time windows.

    Under the hood

    Features come from packet fields such as TCP flags, length and window size. A window is labelled an attack when most of its packets are attack packets (over 80%).

  4. 4

    Detect with an ELM

    An Extreme Learning Machine classifies each window as normal or attack.

    Under the hood

    Its weights are tuned by an improved Whale Optimization Algorithm (a dual optimization). I compared this against a vanilla ELM.

  5. 5

    Locate suspicious IPs

    A second algorithm, run in the switch, pinpoints which source addresses are sending the attack.

    Under the hood

    Controlled by tunable thresholds. I rescaled one from 10000 to 150 so it fits a small Mininet network.

  6. 6

    Maintain the suspicious list

    The control plane confirms and keeps track of the attack sources.

    Under the hood

    This is the list-maintenance part of the paper's mitigation stage.

  7. 7

    Deploy mitigation rules

    Block rules are pushed from the controller into the switch's match-action table.

    Under the hood

    Done through P4Runtime. Register values are read through the BMv2 Thrift CLI.

  8. 8

    Evaluate

    Scores the run on detection rate, false-alarm rates, precision and response times.

    Under the hood

    The same scoring the paper uses: CR, FNR, FPR, DR, precision and Jaccard index. A live-traffic capture pipeline supports retraining.

What comes out. A Fig. 6-style event log (detect, confirm sources, deploy rules, reset), the evaluation metrics, and charts. Caveat from the README: offline evaluation uses a Python simulation of the data-plane modules, and the live path runs the P4 program on BMv2 inside Mininet.

Asks whether a person's phone habits can predict their self-reported productivity, comparing three models, and wraps the analysis in an interactive dashboard.

  • R
  • Shiny
  • XGBoost
  • 10,000 rows
  • 26 columns
  1. 1

    Load the data

    A mobile-usage dataset of 10,000 users and 26 columns: usage, notifications, sleep, device, demographics, and the productivity score.

  2. 2

    Check data quality

    Counts missing values before any modelling.

    Under the hood

    This is the first step of the exploratory script.

  3. 3

    Explore correlations

    Looks at how strongly each habit relates to the productivity score.

    Under the hood

    Daily screen time stands out with a correlation of about -0.85. Age and gaming hours show almost none on their own.

  4. 4

    Set a baseline

    A simple one-feature model gives something to beat.

    Under the hood

    A GLM and a decision tree (rpart), both using screen time only.

  5. 5

    Compare the final models

    Trains a linear regression and an XGBoost model on the same data.

    Under the hood

    Linear regression (screen time and gaming) reached an RMSE of about 9.94. XGBoost (1,000 rounds, depth 4) reached about 9.99.

  6. 6

    Interpret the result

    Both models land at nearly the same error.

    Under the hood

    That suggests the relationship is mostly linear and driven by one dominant feature, rather than complex interactions.

  7. 7

    Explore it in a dashboard

    A Shiny app lets you change predictors, model and train/test split, and run it live.

    Under the hood

    Four tabs: Overview, Correlation Explorer, Model Performance (RMSE, MAE and a predicted-vs-actual plot), and Predict for custom inputs.

What comes out. Two scripts for the fixed reference runs and a dashboard for experimenting. Next steps listed in the README: regularised regression, encoding categorical features, and cross-validation.
